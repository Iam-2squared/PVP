# 見た目を保つ性能改善

更新日：2026-10-28

城壁・王城・街並み・小物の造形と配置を保ち、重複した頂点データと不要な反復処理を減らしています。建物や装飾を間引く処理、描画解像度や画質設定の引き下げは行っていません。

スマートフォン実機のFPS・メモリは未測定です。Linux上のGodot Compatibility／Mesa llvmpipeによる描画時間は、同じ環境での変更前後の比較として扱います。ソフトウェア描画の数値を、そのままスマートフォンの速度には換算しません。

## 重複頂点の共有

同じ位置にある頂点でも、色や法線が違うものは分けたままにします。位置・法線・接線・色など、保存された全属性のバイト列が完全に同じ頂点だけを共有する方式です。面を減らしたり、ボクセルの形を変えたりしません。

| 王都の20部品・頂点共有化のみの集計 | 変更前 | 変更後 |
|---|---:|---:|
| 頂点数 | 3,382,996 | 2,452,875 |
| 三角形数 | 1,690,984 | 1,690,984 |
| メッシュ数 | 389 | 389 |
| サーフェス数 | 389 | 389 |
| 部品ファイルの合計 | 21,406,306 bytes | 19,594,900 bytes |

頂点は930,121個、**27.49％削減**しました。389メッシュのうち370メッシュを共有化し、この段階の部品ファイルの合計は8.46％小さくなりました。ファイルサイズの集計に `generated/kingdom.scn` は含みません。

採用状態の `generated/kingdom.scn` を含む21シーンの合計は19,734,798 bytesです。計測JSONの設計情報を保ち、ファイル量と最適化の記録を更新しています。

三角形を元の順序に展開し、各頂点の全属性のバイト列が一致することを確認しています。さらに、材質、AABB、ノードの配置・変換・影・可視性・メタデータ、衝突形状を照合しました。20部品すべてで保存後に読み直した候補の検証が通ってから置き換えています。

保存ファイル自体のハッシュは変わります。同一性の根拠は、再保存後の三角形ごとの全属性と、変更対象外のシーン・衝突データの照合です。[部品別の検証結果](mesh-optimization-stats.json) に元ファイル・保存後ファイル・照合用のSHA-256を記録しています。

## クライアントの反復処理

対戦HUDは、HP・MP・接続状態・入力・メッセージなど、表示内容が変わったときに再描画します。画面サイズに応じた操作領域とパネル装飾を再利用し、サイズ変更時に更新します。矢・魔法弾は同じ形・材質のリソースを共有し、停止中の武器・カメラや変化のない頭上ラベルへの再設定も減らしました。

変更前後の比較では、3解像度の操作領域、通常・強攻撃の武器とカメラ、他プレイヤーの移動・アニメーション・ラベル、弾の形とリソース再利用など244項目を確認しました。ホーム連携45項目、実クライアントとサーバーの一連の操作40項目、非表示HUDの入力6項目も合格しています。

局所的な反復呼び出しの計測も行っていますが、経路ごとに効果が異なり、全体のFPS改善率としては使いません。[クライアントの計測と回帰結果](performance-client.json) に反復回数、変更前後の3試行、中央値、比較方法を記録しています。ここでのアニメーション比較は変換・状態の照合であり、画素比較とは区別しています。

## 非表示のホーム・職業プレビュー

ホームや職業カードが隠れている間は、そのプレビューのアニメーション処理を停止し、表示すると再開します。変更前から、隠れたプレビューのGPU描画は止まっていました。今回減らすのは背景で残っていたCPU処理です。

非表示中の60フレームで更新が止まり、再表示後にアニメーションが再開することを確認しました。ホーム・男性6職・女性6職の3画面は、1280×720の変更前後画像のRGBAバイト列が完全一致しています。既存のホーム・職業表示281項目とホーム連携45項目も合格しました。

[プレビューの検証結果](performance-frontend.json) に、3画面の変更前後のSHA-256と計測範囲を記録しています。この小さな背景処理の削減だけで、ゲーム全体が大幅に速くなるとはしていません。

## Web配信の転送量

`tools/serve_preview.py` は、書き出したWASM・PCK・JavaScriptのgzip版を用意し、対応するブラウザーへ圧縮して配信します。展開後のバイト列は元のファイルと完全に一致します。ゲームのグラフィックや中身を変えず、読み込み時の転送量を減らす変更です。

ファイルの種類を示すMIMEと、Godot Web版に必要なCOOP・COEPヘッダーを維持しています。原本の更新や圧縮ファイルの不整合時は原本を配信します。Pythonの標準ライブラリだけで動作し、事前に圧縮ファイルだけ準備することもできます。

```sh
python3 tools/serve_preview.py --directory build/web --prepare-only
python3 tools/serve_preview.py --directory build/web --port 8080
```

最終のWeb書き出しで、次の5ファイルの合計が58,938,192 bytesから29,864,717 bytesへ、**49.33％削減**されました。HTTPヘッダーやHTMLなどを含めたページ全体の転送量ではありません。

| 配信データ | 原本 bytes | gzip bytes |
|---|---:|---:|
| WASM | 37,700,666 | 9,436,629 |
| PCK | 20,911,496 | 20,346,080 |
| JavaScript 3ファイル | 326,030 | 82,008 |
| 合計 | 58,938,192 | 29,864,717 |

5ファイルすべてで展開後のSHA-256と原本が一致しています。[転送量とファイルごとの照合結果](performance-transfer.json) に記録しています。Webクライアントが参照しない計測JSONとサーバー専用シーンも配布対象から外し、表示する王都と物の配置は維持しています。

小さなfixtureでは、展開後の一致、HTTPの圧縮選択、キャッシュ、HEAD、原本への切り替えなど7テスト群が合格しました。

```sh
python3 tools/test_serve_preview.py
```

## 対戦サーバーのメモリ

画面を描かない専用サーバーは、王都の既存の衝突形状と共有データだけを読み込みます。クライアントが表示する街並みはそのままです。専用シーン `generated/server_kingdom.scn` はWebクライアントの書き出しから除外しています。

最終の頂点共有化後の王都と比較した別プロセス計測では、シーン読み込み後のGodot管理メモリが292,654,576 bytesから220,861,680 bytesへ減り、**68.47MiB削減**しました。両プロセスの読み込み前の基準値は同じ21,865,739 bytesです。OSの常駐メモリやGPUメモリの計測ではありません。読み込み時間はファイルキャッシュなどの影響を分離した比較ではないため、速度比較には使いません。

273個の衝突形状、衝突1,132,220三角形、共有データ、対戦時の4つの門は一致しています。60Hzの物理処理は維持し、サーバープロトコル66項目、6職の戦闘32項目、ホーム連携40項目が合格しました。詳細と計測条件は [サーバーの検証結果](performance-server.json) を参照してください。これはサーバーの使用メモリの改善であり、スマートフォンの描画速度を測った結果ではありません。

最終ソースでは、成長・ホーム・サーバー・戦闘・入力の8本、計590項目が失敗・スキップとも0で合格しています。項目ごとの結果は [対戦の検証表](battle.md) とサーバーの検証JSONに記録しています。

## 描画の最終比較

採用した王都は、全20部品のファイルハッシュが検証済みの頂点共有化後の値と一致しています。南門・市場通り・王城前・上空の同じ位置、同じ1280×720で比較し、4視点すべてのRGBAバイト列が変更前と完全一致しました。

次の数値はMesa llvmpipeによる各20フレームの中央値です。ソフトウェア描画の環境によるばらつきがあり、視点によって変化も異なります。市場通りでは短縮していないため、ゲーム全体やスマートフォンで一定のFPS改善があるとはしていません。

| 視点 | 変更前の中央値 ms | 変更後の中央値 ms | 画像の照合 |
|---|---:|---:|---|
| 南門 | 1,000.851 | 832.028 | RGBA完全一致 |
| 市場通り | 358.590 | 369.577 | RGBA完全一致 |
| 王城前 | 403.064 | 402.292 | RGBA完全一致 |
| 上空 | 358.612 | 342.007 | RGBA完全一致 |

[描画と同一性の検証結果](performance-rendering.json) に元の計測値、画素のSHA-256、最終20部品のハッシュを記録しています。これはHUD・プレイヤー処理を止めた固定視点の比較で、オンライン対戦全体の速度測定とは分けています。

影用の頂点共有と描画順の最適化も試しましたが、頂点共有化だけの場合と近い速度にとどまりました。検証用headlessプロセスの管理メモリ約16.5MB増と、ファイル約6.5MB増に見合わなかったため採用していません。採用状態にはこの追加データを含めず、元の面順と影の設定を維持しています。

## 右半分の視点操作

視点用の指は、画面右半分のボタン以外から新しく触れたときだけ受け付けます。左の移動スティックや攻撃・ジャンプ・スキル・帰還の指と分け、中央線をまたいだときや画面回転・キャンセル・帰還・復帰時の入力状態も整理しました。操作ボタンの見た目や配置は維持しています。

ScreenTouch・ScreenDragイベントを入力経路へ渡す回帰と、PCのマウスキャプチャを含め、ウィンドウ表示で64項目が合格しました。headlessでは61項目が合格し、実際のマウスキャプチャが必要な3項目をスキップします。手順は [対戦の操作と検証](battle.md) にあります。

## 計測・再生成

重複頂点の検証だけを再実行する場合：

```sh
godot --headless --path . --script res://tools/optimize_voxel_meshes.gd -- --dry-run --report=res://captures/mesh-weld-recheck.json
```

既に共有化した部品では、追加で削減する頂点が0になることがあります。変更前の部品との照合記録は、保存済みの部品別JSONを参照してください。

サーバー専用シーンの生成と一致確認：

```sh
godot --headless --path . --script res://tools/bake_server_world.gd
godot --headless --path . --script res://tools/bake_server_world.gd -- --verify-only
```

既存部品を再生成・最適化した後は、サーバー専用シーンと検証レポートも更新します。

描画できる環境での比較用キャプチャと計測：

```sh
godot --path . --script res://tools/benchmark_rendering.gd -- --output=res://captures/render-benchmark --frames=20
```

描画計測はheadlessでは実行できません。計測ツールは比較中のFPS上限を解除し、ドライバーにVSyncの解除を要求します。ゲーム本体の画質や解像度の設定を変更するものではありません。

対戦の回帰確認は [対戦と成長の説明](battle.md) のテスト手順を参照してください。通信とクールダウンは実時間を使うため、対戦サーバーのテストに `--fixed-fps` は指定しません。
